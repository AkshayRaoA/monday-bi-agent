# Decision Log — Monday.com Business Intelligence Agent

## 1. Key Assumptions

The solution assumes that the Deals board represents the sales pipeline
and the Work Orders board represents project execution and associated
financial information.

For pipeline analysis, a deal is considered active when its Deal Status
is either `Open` or `On Hold`. `Won` and `Dead` deals are excluded from
active pipeline calculations.

For month- and quarter-based pipeline analysis, the `Tentative Close Date`
is used because it represents the expected closing timeline for active
opportunities.

Missing monetary values are treated as unknown rather than zero. This is
important because a missing deal value does not necessarily mean that the
deal has no value.

The supplied Deals and Work Orders data do not contain a consistently
reliable shared identifier. Therefore, the prototype does not automatically
join records across the two boards unless a relationship can be established
safely. This avoids producing misleading cross-board conclusions.

The source data is treated as intentionally messy. Data cleaning is therefore
performed in the application rather than manually fixing every value in the
monday.com boards.

## 2. Technical Decisions and Trade-offs

### monday.com GraphQL API instead of MCP

I chose the monday.com GraphQL API because the application works with two
known boards and requires direct control over board IDs, columns, item
retrieval, authentication and error handling.

The integration is read-only. The application never modifies monday.com
records.

### Python and Pandas

Python was chosen because it provides simple integration with HTTP APIs,
data-cleaning tools and rapid application development.

Pandas is used for filtering, normalization and deterministic calculations
such as pipeline value, receivables, collections and execution status.

### Streamlit for the interface

Streamlit was chosen because the assignment requires a hosted prototype
rather than a production frontend.

Using Streamlit allowed development effort to focus on data quality,
business intelligence and integration rather than frontend complexity.

### Deterministic analytics instead of LLM calculations

The original design supported an LLM-based interpretation layer. However,
the final prototype uses deterministic conversational routing so that it can
run without a paid AI API dependency.

Business numbers are always calculated by Python functions rather than being
generated by a language model.

The trade-off is that the system is less flexible for completely unexpected
phrasing, but it is more predictable, inexpensive and reliable for supported
business questions.

The conversational layer supports aliases, fuzzy sector matching and
clarifying responses for ambiguous questions.

## 3. Data Resilience Decisions

The application handles several real-world data issues found in the supplied
datasets:

- missing deal values
- missing close dates
- missing execution status
- inconsistent capitalization
- embedded header-like rows
- missing billing information
- missing collection amounts
- negative receivable values
- inconsistent sector labels

Statuses and sectors are normalized before analysis.

Dates are parsed safely, and invalid or missing dates are excluded only from
calculations that require dates.

Missing financial values are preserved as unknown rather than automatically
converted to zero.

The application communicates important data-quality caveats alongside
business results.

For example, if pipeline records are missing deal values, the system reports
the known pipeline value and explains that the true pipeline may be higher.

## 4. Interpretation of "Leadership Updates"

I interpreted "help prepare data for leadership updates" as producing a short
executive-level summary instead of simply exporting rows from monday.com.

The Leadership Update combines information from both boards and highlights:

- active sales pipeline
- pipeline concentration by sector
- work-order execution
- delayed projects
- billed amounts
- collections
- receivables
- amount remaining to be billed
- important data-quality issues

The objective is to surface information that a founder or senior executive
can quickly use during a leadership review.

## 5. What I Would Do Differently With More Time

With more development time I would add:

- LLM-based natural-language intent extraction for more flexible questions
- monday.com OAuth instead of a single API token
- historical snapshots for trend and period-over-period analysis
- stronger cross-board entity matching
- configurable probability weighting for pipeline forecasting
- charts and drill-down visualizations
- automated unit and integration tests
- role-based access controls
- monitoring and application observability
- source-level citations linking answers to individual monday.com records

The current prototype prioritizes reliable calculations, transparent
data-quality handling and a simple hosted experience.
